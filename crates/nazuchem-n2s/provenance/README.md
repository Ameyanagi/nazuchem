# Pinned source and migration evidence

Source: [OPSIN main (3.0-SNAPSHOT)](https://github.com/dan2097/opsin/tree/42e87ac6efb1bd9f578986f5ea7ee1faa8e93c91),
commit `42e87ac6efb1bd9f578986f5ea7ee1faa8e93c91`, MIT license,
copyright 2017 Daniel Lowe. The original port was based on OPSIN 2.9.0,
`b91b610af5ab07560fedb20730d7aef46bb2bca0`; every later upstream change that
affects parsing or structures is ported through the pinned main commit,
including phane nomenclature (see `../PORTING.md`).
`../LICENSE` is an unmodified upstream copy. `manifest.json` records every
XML/DTD file, migrated table, exporter and fixture hash. The seven DTD files
and 33 XML files are byte-equal to the pinned main checkout. The native
`regexTokens.xml` extensions permit a locant before an axial descriptor and
recognize unlocanted Xi/xi stereodescriptors, and read two chalcogen symbols
such as `SO-` as the locant of a peroxy ester's organyl group (IUPAC
P-65.6.3.3.7.1). The native `regexes.xml` extension permits `ene`/`yne` after
the closing bracket of a spiro name (P-31.1.5.2.1, P-31.2.3.3.3). The native `multipliers.xml`
additions supply the composite P-14.2 numerical terms. The native
`inlineSuffixes.xml`, `suffixApplicability.xml` and `suffixRules.xml`
extensions add the `aminiumyl` and `aminiumylidene` substituent suffixes
(IUPAC P-73.6). Native dictionary additions to `suffixes.xml`,
`suffixRules.xml`, `suffixApplicability.xml` and `functionalTerms.xml` read
chalcogen peroxy acids and their `ate` forms, peroxols, tellanal, mixed-chalcogen peroxyanhydrides
and peroxide class names. Native `simpleSubstituents.xml` tokens read the
acid-anion prefixes of chalcogen-replaced sulfinic and sulfonic acids, such as
`sulfinothioato` (P-72.6.1, P-65.3.1.3). These additions only add dictionary tokens to
existing token lists, so the DFA tables are unchanged. `native_extensions` in
the manifest records these changes.

The development oracle is the main build
`opsin-core-3.0-SNAPSHOT-jar-with-dependencies.jar`, SHA256
`931be2952b290dea62548a3bb4129703078c763576a836ac99d8a54d30083f03`.
It is never embedded, loaded, spawned or downloaded by this Rust crate.
Cargo builds and tests consume only native resources and frozen fixtures.

`ExportDfa.java.txt` is a record of the one-time data migration program, not a
Cargo input. It reads upstream `RunAutomaton` tables and emits a neutral binary
format; Rust does not parse Java serialization. All 48 automata are exported:
chemical grammar in both directions, and 23 DFA token recognizers in both
directions. The two remaining regex tokens are the directly ported zero-width
ASCII-letter boundary predicates `Ă` and `ă`.

The table format is big endian: `OPSINDFA`, u32 format version 2, u32 automaton
count; per automaton, u32 ASCII-name byte length and name, u32 initial state,
u32 state count, u32 character-interval count and those u32 UTF-16 intervals;
per state, u8 acceptance flag and u32 transition count, then (low UTF-16 code
unit, high UTF-16 code unit, target state) u32 triples. Omitted transitions
reject. Adjacent equal-target intervals are merged. Original state IDs and
annotation-interval ordering are retained. The exported table SHA256 is recorded
in `manifest.json`; the regenerated tables include the forward/reverse `phaneLocants` recognizer and shared locant
and stereochemistry grammar changes.

The documented export process attributes the native `regexTokens.xml`
extensions to `token-69`, the stereochemistry bracket recognizer (locanted
axial and unlocanted Xi/xi descriptors), and to `token-108`, the locant
recognizer (peroxy ester locants), each with its reversed table. The
`regexes.xml` extension changes the chemical grammar tables `chemical` and
`chemical-reversed`. The checked table is a full export with the checked
`regexTokens.xml` and `regexes.xml` as development resource overrides. A
pristine export (no override) differs from it in those six tables only. An
automaton built from an overridden file gets its state numbers from dk.brics
in an order that varies between runs, so a rebuild of the pinned jar with
`scripts/regenerate_opsin_grammar.py` reproduces the same automata, not always
the same bytes; the script keeps the checked table whenever the fresh export
equals it after renumbering every automaton's states breadth first. Cargo reads the
checked binary directly. Frozen upstream oracle fixtures are unchanged.

## Regenerating the grammar table

`automata.bin` and every hash that pins it are regenerated by
`scripts/regenerate_opsin_grammar.py`. It needs JDK 21 and the pinned jar;
Temurin 21.0.13 reproduces the checked table byte for byte. Both install
without root, and no shell profile needs to change. On macOS aarch64 (pick the
matching asset name on other platforms):

```sh
mkdir -p ~/.local/opt && cd "$(mktemp -d)"
base=https://github.com/adoptium/temurin21-binaries/releases/download/jdk-21.0.13%2B9
jdk=OpenJDK21U-jdk_aarch64_mac_hotspot_21.0.13_9.tar.gz
curl -fsSLO "$base/$jdk" && curl -fsSLO "$base/$jdk.sha256.txt"
shasum -a 256 -c "$jdk.sha256.txt" && tar -xzf "$jdk" -C ~/.local/opt
mvn=apache-maven-3.9.16-bin.tar.gz
curl -fsSLO "https://dlcdn.apache.org/maven/maven-3/3.9.16/binaries/$mvn"
curl -fsSL "https://downloads.apache.org/maven/maven-3/3.9.16/binaries/$mvn.sha512" -o mvn.sha512
echo "$(cut -d' ' -f1 mvn.sha512)  $mvn" | shasum -a 512 -c && tar -xzf "$mvn" -C ~/.local/opt
```

The JDK home is `~/.local/opt/jdk-21.0.13+9/Contents/Home` on macOS
(`~/.local/opt/jdk-21.0.13+9` on Linux). Build the jar from a worktree of the
pinned commit, passing `JAVA_HOME` and `PATH` per command:

```sh
opsin=/path/to/opsin-pinned-42e87ac
git -C /path/to/opsin worktree add --detach "$opsin" \
  42e87ac6efb1bd9f578986f5ea7ee1faa8e93c91
JAVA_HOME=~/.local/opt/jdk-21.0.13+9/Contents/Home \
PATH=~/.local/opt/jdk-21.0.13+9/Contents/Home/bin:~/.local/opt/apache-maven-3.9.16/bin:$PATH \
  mvn -B -q -f "$opsin/pom.xml" -pl opsin-core -am -DskipTests package
```

This writes `$opsin/opsin-core/target/opsin-core-3.0-SNAPSHOT-jar-with-dependencies.jar`.
Maven stores build times in the zip entries, so a rebuild never matches the
oracle's file SHA256 above. The script accepts either that file or a jar whose
content SHA256 (sorted entry names and uncompressed bytes) is
`84949d143459a3de91b9d0483910832e70ee26c7a550380a012250a878c09de5`, the value
two clean builds with Temurin 21.0.13 and Maven 3.9.16 produced. Then, from
the nazuchem repository root, run:

```sh
OPSIN_JAR=$opsin/opsin-core/target/opsin-core-3.0-SNAPSHOT-jar-with-dependencies.jar \
JAVA_HOME=~/.local/opt/jdk-21.0.13+9/Contents/Home \
  uv run --no-project python scripts/regenerate_opsin_grammar.py
```

`--jar` and `--java-home` replace the environment variables, and `--check`
reports stale files without writing. The script compiles `ExportDfa.java.txt`
and runs it in a fresh temporary directory. Each of `regexes.xml`,
`regexes.dtd`, `regexTokens.xml` and `regexTokenList.dtd` (the only files the
automata are built from) that differs from the jar's upstream copy is placed
under `resources/uk/ac/cam/ch/wwmm/opsin/resources/` as an override; today that
is `regexTokens.xml` and `regexes.xml`. Unchanged files are deliberately not overridden:
loading more files from disk renumbers the states of freshly built automata
(`token-69`), producing an isomorphic but byte-different table. The script then
rewrites `resources/automata.bin`, the `manifest.json` resource hashes and
resource fingerprint, `RESOURCE_FINGERPRINT` in `src/lib.rs`, the constant
below, and the `PROVENANCE-nazuchem.toml` hashes of the resources, the manifest
and this file.

A grammar change (`regexTokens.xml` or the chemical grammar in `regexes.xml`)
therefore needs a `native_extensions` entry in `manifest.json` naming the
change and the automata it alters, written by hand, and then the script, which
also pins the edited manifest's hash in the ledger. Dictionary
tokens added to existing token lists in other XML files do not alter the table,
but the script still refreshes their hashes and the fingerprint.

When two branches both change the grammar, `.gitattributes` marks
`automata.bin` binary, so git keeps one side and reports a conflict. Merge the
grammar XML and any prose by hand, then run the script: it accepts conflict
hunks that differ only in hashes it regenerates and rewrites those hashes, and
stops on any other conflict, including one in a hash it does not own.
`tests/resource_pins.rs` fails in CI while any hash or the fingerprint
disagrees with the checked resources.

## Fixture exporters and resource fingerprint

`ExportFrontend.java.txt` records the frozen frontend fixture generator. Its
first argument is a UTF-8 file of distinct input names (one per line); its
second argument is the output JSONL path. Inputs comprise the first tab-separated
column of each nonblank, noncomment line in the 31 upstream integration resource
files, in filename/line order, followed by explicit tokenization edge cases.
Deduplication preserves first occurrence. Every name is processed through
upstream `PreProcessor` before six lexical modes are captured. The checked
fixture contains 1,350 names × six modes, requiring no live oracle in tests.

`ExportParseTrees.java.txt` records complete Parser output and stable SortParses
ranking for 1,359 names under four configurations: radicals false/true crossed
with detailed failure analysis false/true. `parse-tree-golden.jsonl.gz` has
5,436 records, including exact ordered XML attributes and errors. Its native
differential gate passes all records.

`ExportComponents.java.txt` uses the same tab-separated family/name input and
four configurations. After upstream ranking, it captures each candidate's XML
before and after ComponentGenerator, or its error, and ordered warnings. The
5,436 rows contain 5,932 candidates. `component-golden.jsonl.gz` therefore
supports testing transformations independently of the Rust frontend.

`ExportFusedNumbering.java.txt` takes tab-separated test name, SMILES and
expected labels. `fused-numbering-inputs.tsv` includes all 81 active
FusedRingNumbererTest examples. The frozen JSONL records SSSRFinder's ordered
atom/bond lists, final atom ordering, per-original-atom locants, and errors.

`ExportFusedBuilding.java.txt` reads compact root XML from
`fused-building-inputs.tsv`, attaches the root to a dummy word (the same
context required by ComponentProcessor), resolves each group with numeric
labels, and applies FusedRingBuilder. The 11 captured records compare ordered
XML and fragment atom/locant/spare-valency/bond snapshots, including failures.
`ExportSuffixRules.java.txt` captures all 997 group/suffix/subtype queries in
`suffix-rule-inputs.tsv`, including null, empty and mismatching subtypes and
unknown types/suffixes. It records ordered tags/attributes and exact errors.

`ExportStructures.java.txt` captures all 1,312 active integration rows twice,
under strict defaults and with radicals allowed; all other flags remain false.
The 2,624 records in `structure-golden.jsonl.gz` include status, message,
ordered warnings, plain SMILES, semantic CXSMILES (mask 13), and a lossless
ordered graph with explicit hydrogen atoms, charge, isotope, valency and stereo
references/groups. Capturing a fixture does not establish native equivalence;
the migration ledger records executed acceptance gates separately.

`ExportConfigurations.java.txt` crosses all five configuration flags for each
name in `configuration-inputs.txt`. The 20 names include upstream configuration
test examples, polymer/radical/stereo cases and failure analysis edges. All
640 frozen complete result records are exercised without a live oracle.

Compile each development exporter with the pinned JAR and the compiled
ExportFrontend class on its classpath; the latter supplies JSON quoting. Run
from a fresh working directory with absolute input/output paths. Exporter
source and every checked fixture hash are recorded in `manifest.json`.
Its historical `ExportDfa.java.txt` hash predates the extraction's
provenance-comment correction; the exporter body is unchanged and
`PROVENANCE-nazuchem.toml` at the repository root records its current hash.
Compressed JSONL uses gzip level 9 with timestamp zero and an empty filename.

The resource fingerprint is SHA256 over each resource in sorted UTF-8 path
order, concatenating path, NUL, raw file bytes, NUL. This independently covers
all XML/DTD files and the neutral DFA table. The exported crate constant is
`81993f21f823a6b887a8085c60914d5d7a6d634981c55469abd1d0d251dd67a6`.

`ExportGraphResources.java.txt` captures every distinct literal resource
`(value, type, labels)` triple. The current gate checks 2,643 ordered graph
snapshots and constructs all 3,183 literal groups. `phanes.txt` contributes
174 integration names (348 strict/radical structure records); the 21 phane
rows in `uninterpretable.txt` are also checked natively. No goldens are edited
by hand. Regeneration uses the checked exporter sources and the pinned jar.
